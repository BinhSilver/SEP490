## Task 7 rulings (Dialogue trustworthy completion)

- Ruling: Dialogue is deliberately **not** built on `InteractiveStudyEngine`/`InteractiveContentAdapter`, unlike Vocabulary/Kanji/Grammar. The engine's shape is "flip-or-practice gate → issue/submit/grade/attempt-cycle/cooldown/review", and Dialogue has none of that — no card, no question, no score, no pass/fail, no attempt limit. Forcing it through the engine (e.g. by inventing a fake always-one-question "micro-check") would fabricate a scored artifact the spec explicitly says must not exist (§2 "Hội thoại là điều kiện hoàn thành, không tham gia điểm"). `InteractiveDialogueService`/`InteractiveDialogueServiceImpl` is instead a small, standalone parallel service — same ownership/locking idioms (`findOwnedByIdForUpdate`, `PESSIMISTIC_WRITE` on its own progress row, revision-bump reset) borrowed from Grammar's practice-gate precedent, but its own state machine. — cost if wrong: none identified; this is an architecture decision stated explicitly per the governing instructions' request, and it does not block Task 8 from reading `activityState == COMPLETED` as Dialogue's done-signal instead of `PASSED`.
- Ruling: the server **never accepts a client-reported duration, elapsed time or timestamp** for the heartbeat — only an opaque `heartbeatToken` used purely to detect an exact replay. All timing math (`gapSeconds = serverNow - lastHeartbeatAt`, capped at 20s, reset to 0 credit above a 30s gap) is computed from the server's own clock and the previously *persisted* `lastHeartbeatAt`. This makes the "cap even a heartbeat reporting a huge elapsed value" requirement automatically true by construction — there is no code path where a client value influences `accumulatedSeconds` at all — rather than something that needs a separate defensive clamp on a client-supplied number. — cost if wrong: a genuinely slow/delayed HTTP request could under-credit a learner a few seconds near a cap/reset boundary; acceptable, since the alternative (trusting client-reported elapsed time) is the exact tampering vector the task exists to close.
- Ruling: reached-bottom evidence requires **at least one prior heartbeat to exist** (a `learning_dialogue_progress` row must already be present) or it is rejected with `VALIDATION_FAILED`. This is the concrete, testable interpretation of "bottom-reached tampering ... is rejected" — the server has no way to verify actual DOM/scroll state, so the closest honest proxy for "not obviously tampered" is "some real engagement (a heartbeat) happened first," not a bare cold call to `/reached-bottom` from a script that never opened the page. — cost if wrong: a learner who scrolls to the bottom faster than the first 15s heartbeat interval fires would transiently see a rejection; mitigated by the frontend sending an immediate heartbeat on mount (before starting the 15s interval), so in practice a heartbeat always precedes any possible bottom-reached call by design, not by accident.
- Ruling: completion (`completed_at`) requires **both** `accumulated_seconds >= 180` **and** `reached_bottom_at IS NOT NULL`, checked identically after every heartbeat and every reached-bottom call (one shared `applyCompletionIfEligible` helper), and is set at most once — subsequent calls that still satisfy both conditions do not move the timestamp. No Dialogue score field exists anywhere (DTOs, entity, schema) — this is intentional per spec §2 and is called out explicitly so Task 8's package-score calculation has nothing Dialogue-shaped to accidentally include in a numerator/denominator.
- Ruling: dialogue script content (Japanese text, translation, role, scene/bubble metadata, audio URL) is read through the **existing** dictionary-module repositories `DialogueLineDetailRepository` (already had `findAllById` for free via `JpaRepository`) and `ContentAudioRepository` (already had `findByOwnerTypeAndOwnerIdIn("CONTENT_ITEM", ids)` for free) — zero new methods, zero modified files in `com.jlas.dictionary`, matching the hard boundary "never modify the source dialogue/textbook module." Membership canonical ids are `content_item.id` values already snapshotted by Task 3's composer (`JpaInteractiveContentCatalog`/`InteractivePackageComposerImpl`, unmodified).
- Ruling: no genuine Task 4/5/6 bug was found while building Task 7 (unlike Task 6, which found two in Task 5's scope) — the engine, Grammar's practice-gate pattern and the `pageCss` convention were all reused correctly on inspection; no narrowly-scoped fix was needed this session.
