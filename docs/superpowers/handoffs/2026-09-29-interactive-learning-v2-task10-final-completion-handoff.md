## 4. Summary page — what it shows and how it's computed

**Route:** `GET /learning/path/v2/summary` (page) → `GET /api/learning/v2/paths/current/summary` (data,
`InteractiveLearningPathController.summary`, `ApiResponse<InteractivePathSummaryResponse>`).

**Ownership:** resolves the caller's most recent `INTERACTIVE_V2` path (`UserLearningPathRepository
.findTopByUserIdAndExperienceVersionOrderByIdDesc`) — deliberately **not** the `ACTIVE`-only lookup `current()`
uses, so the summary stays reachable once the path has transitioned to `COMPLETED` (see §6). Never accepts a
path id from the caller.

**Per-skill (Vocabulary/Kanji/Grammar) first/latest/best**, aggregated across **every activity of that type
anywhere in the path** (not one package — a skill can appear in multiple target/warm-up days):

- Loads all `UserLearningPathItem` for the path, filters by `activityType`, batch-fetches every
  `LearningMicroCheckState` for those activity ids in one query
  (`LearningMicroCheckStateRepository.findByActivityIdInOrderByActivityIdAscBatchIndexAsc`, new).
- `firstScore` = the earliest-created attempted state's own `firstScore`; `latestScore` = the
  most-recently-updated attempted state's own `latestScore`; `bestScore` = the max `bestScore` across all
  attempted states. None of the three is ever re-derived from the others or averaged.
- `hasEvidence = false` (never "0%") when no batch of that skill has ever had a valid submit
  (`attemptsUsed > 0`) anywhere in the path.
- **Unresolved dimensions are named explicitly, at batch granularity**: any attempted batch that is not
  currently `passed` is listed as `{activityId, batchIndex, latestScore, reviewRequired, cooldownUntil}`.
  `resolved = unresolved.isEmpty()`. This is the concrete mechanism that prevents a learner who is 95% on two
  skills from having a third, still-failing skill averaged away — the failing batch is named, not hidden.

**Dialogue**: a plain `{totalCount, completedCount, allCompleted}` — never a percentage, since Dialogue has
no score field anywhere in the schema by design (Task 7/8).

**Reading/Listening (`comprehension`)**: read exclusively from the Smart Test snapshot via the existing,
optional-autowired `LearningProfileSource.loadForUser(userId, assessmentAttemptId)` — the exact same
read API Warm-up B (Task 9) already uses, best-effort/non-fatal (missing/broken data degrades to "no
evidence", never blocks the rest of the summary). `note` on every comprehension entry always states plainly
that this skill was not re-evaluated inside the Learning Path itself. `weak` reuses
`WeakTagPolicy.comprehensionLessonCount(SkillScore) > 0` verbatim (the same approved 0/4/6/8 boundary Task 9
already uses).

**Readiness confidence**: `LOW` if any scored skill has no evidence yet, or is unresolved, or Reading/
Listening has no Smart Test sample; otherwise `MEDIUM` — **deliberately capped, never `HIGH`**, because
Reading/Listening is never re-verified inside the path itself (see §11 for why this stays a gap). The
`explanation` string always names the concrete gap or evidence behind the level.

**`certificateEligible`**: true iff at least one `GOAL_LEARNING` package exists for the path and every one of
them is `COMPLETED` (warm-up packages are prerequisites, not counted requirements). This is the exact same
check the certificate page itself enforces — see §5.

## 5. Certificate — entity/schema, idempotency/ownership, exact wording

**No schema change, no certificate table.** Follows the existing, approved V1 precedent
(`LearningCertificatePageController`, `templates/learning/certificate.html`): the certificate is derived
read-only from path/package completion state that `InteractiveLearningPathServiceImpl` already owns and
guards exactly-once (Task 8's pessimistic-lock + `status != COMPLETED` guard). There is nothing to persist —
adding a table would only create a second place this data could drift from the source of truth.

**Route:** `GET /learning/v2/certificate` (`InteractiveLearningCertificateController`, new). Calls
`InteractivePathSummaryService.summary(userId)` (already principal-scoped and unit-tested) rather than
re-deriving the eligibility gate a second time — refuses with `NOT_FOUND` if `certificateEligible` is false,
then re-verifies the resolved path's `user.id` equals the principal's id defensively before rendering.

**Exact wording used, verbatim, in the page's `<h1>`:** **"Chứng nhận hoàn thành lộ trình J-LAS"**. The page
also states explicitly: *"...không phải điểm số hay chứng chỉ JLPT chính thức và không xác nhận người học đã
đỗ kỳ thi JLPT."* No wording anywhere implies a JLPT pass or an official certificate.

**Idempotency**: trivial by construction — the page performs no write at all, so "issuing twice" is not a
state that can occur; any number of requests render the same view from the same underlying, already-
exactly-once-guarded completion state. Verified by
`InteractiveLearningCertificateControllerTest#repeatedRequestsNeverMutateAnythingAndAlwaysReturnTheSameView`.

**Ownership**: `@AuthenticationPrincipal UserPrincipal` only — never a path id from query/body/path used for
authorization (only for lookup, immediately re-checked against the principal).

## 6. Path-level completion — the audit-found bug, fixed

`InteractiveLearningPathServiceImpl` (Task 2/8/9's own file) never set `UserLearningPath.status =
'COMPLETED'` anywhere in the V2 code path — confirmed by grepping every `setStatus("COMPLETED")` call site in
the `learning` service package before writing any Task 10 code; only the legacy `LearningServiceImpl` (V1)
and `LearningPathPackage` (V2, Task 8) had one. Without this, `current()`'s `status = 'ACTIVE'`-only lookup
would keep matching a V2 path forever, even with nothing left to do, and there was no single, unambiguous
path-level signal for summary/certificate eligibility to read.

**Fix** (`InteractiveLearningPathServiceImpl.maybeCompletePath`, called from the existing `refresh(...)`):
once every `GOAL_LEARNING` package for the path is `COMPLETED` (warm-up packages excluded — they are
prerequisites, not counted requirements) and at least one `GOAL_LEARNING` package exists, the path
transitions `ACTIVE → COMPLETED` with `completed_at` set exactly once, guarded by `status != 'ACTIVE'` so it
can only fire once per path. Three new focused tests prove: completion on the sole/last target package,
staying `ACTIVE` while another target package is still open, and a warm-up-only completion never completing
the path by itself.

## 7. Security audit finding, fixed: deterministic question replay across retries

**What was found:** `InteractiveStudyEngine.issueMicroCheck` (shared by Vocabulary/Kanji/Grammar) generated
every batch's questions purely as a function of `(batch content, batchIndex)` — confirmed by reading all
three adapters' `buildQuestions`/`optionQuestion` implementations, none of which contain any `Random`/shuffle
call; rotation depended only on each member's fixed position `i`. This means **every retry of the same
still-unpassed batch reproduced byte-identical questions and option positions.**

Because a failed attempt's feedback (`MicroCheckResult.review`) is a *required*, spec-mandated feature
(design spec §4.5 — immediate explanatory feedback naming the correct answer per question), this feedback
revealed the exact correct answer for every question in the batch — and the very next issue of that same
batch (attempt 2, or attempt 3, or even a fresh cycle after cooldown+review) would show the *same* questions
in the *same* positions. A learner could pass the "three genuine attempts" mastery gate purely by replaying
the revealed answer key from the previous failed attempt, without any real engagement with the content —
silently defeating the integrity assumption every one of Tasks 4-9 built their attempt/cooldown/review
machinery on top of. **None of the six prior task handoffs disclosed this.** They flagged "issue not strictly
idempotent" (an orphaned-snapshot-row concern) and "not race-tested," but never this replay vector.

**Fix:** a server-derived `variationSeed` — the batch's own `attemptsUsed` count *at issue time, before this
call* (never client input) — is threaded through `InteractiveContentAdapter.buildQuestions(batch, batchIndex,
variationSeed)` and folded into each adapter's existing rotation math (`rotateSeed = i + variationSeed`
instead of `rotateSeed = i`). The very first issue of any batch is byte-identical to pre-fix behavior
(`variationSeed = 0`), so no existing test needed a single assertion changed — proven by the full regression
suite staying green unchanged. A new regression test per content type
(`reIssuingTheSameUnpassedBatchAfterAFailedAttemptVariesTheOptionArrangement`, in
`InteractiveVocabularyServiceTest`/`InteractiveKanjiServiceTest`/`InteractiveGrammarServiceTest`) proves a
second issue after one failed attempt produces a different option arrangement. Grading is unaffected in
every case — `submitMicroCheck` always grades against the specific issued session's own immutably stored
`answerKeyJson`, it never regenerates.

**Honest scope of the fix:** this varies the arrangement between attempts *within the same batch's
lifetime*, keyed off `attemptsUsed`. A fresh cycle after cooldown+review resets `attemptsUsed` to 0, so its
first attempt reuses the original arrangement (`variationSeed = 0`) — accepted, since the design already
mandates a genuine review step in between (design spec §4.3), unlike the zero-friction repeat within one
cycle that this fix specifically targets.

## 10. Rate limiting — mechanism and coverage

**Mechanism:** `InteractiveRateLimitService` (new), a per-user, per-named-bucket sliding-window limiter —
the exact in-memory pattern already shipped twice in this codebase
(`com.jlas.shadowing.service.PronunciationRateLimitService`, `com.jlas.moderation.service
.ModerationRateLimitService`), reused rather than adding a new library. Injectable `Clock` for deterministic
tests; production uses `Clock.systemUTC()`.

**Buckets and limits** (all per user, chosen generous for real use, tight enough to block scripted spam):

| Bucket | Limit | Window | Applied to |
|---|---|---|---|
| `MICRO_CHECK_ISSUE` | 20 | 60s | Vocabulary/Kanji/Grammar `POST .../micro-check` |
| `MICRO_CHECK_SUBMIT` | 20 | 60s | Vocabulary/Kanji/Grammar `POST .../micro-check/submit` |
| `DIALOGUE_HEARTBEAT` | 8 | 30s | Dialogue `POST .../heartbeat` (tuned around the design spec's own ~15s cadence) |
| `CERTIFICATE_VIEW` | 20 | 60s | `GET /learning/v2/certificate` |

Applied at the controller layer (one `rateLimit.check(...)` call per endpoint method), not inside the shared
engine — so Grammar's ordering/fill practice endpoints (which have no attempt limit by design, per Task 6's
own ruling that practice is freely retriable) are correctly left unlimited. **Not distributed** — a
multi-instance deployment would need a shared store (e.g. Redis) instead; same accepted limitation as the two
existing limiters this one copies.
